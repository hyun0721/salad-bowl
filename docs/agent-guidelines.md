# 에이전트 공통 작업 규칙

Claude와 Codex가 공유하는 저장소 규칙의 원본이다. 각 실행기의 진입 파일은
이 문서를 참조하고, 같은 정책을 별도로 복제하지 않는다.

## 범위와 협업

- 사용자 요청과 작업 brief의 범위를 지킨다. 기존 패턴·공용 부품·설치된 의존성을
  먼저 사용하고, 요청하지 않은 기능·추상화·의존성을 추가하지 않는다.
- 같은 변경을 구현하는 담당자는 한 번에 하나다. 다른 실행기의 미완료 변경을
  덮어쓰지 않는다. 구현·리뷰·진단 담당과 기준 커밋을 구분한다.
- 독립 리뷰가 필요한 작업이면 구현하지 않은 담당자가 한 번 리뷰한다.
  단독 실행으로 자체 점검한 결과를 독립 리뷰로 표현하지 않는다.
- 위임받은 작업은 brief의 커밋·push·보고 제한을 따른다. Codex가 시작한 작업에는
  Claude의 위임 절차(`codex-collab`)를 적용하지 않는다. Claude 세션은 계획 실행뿐
  아니라 사용자가 직접 요청한 코드 변경에도 그 절차를 적용한다.
- 설계·계획은 `docs/superpowers/specs/`와 `docs/superpowers/plans/`에 있다.
  관련 문서만 읽고 현재 코드와 대조한다. 과거 계획의 담당 모델·플러그인명·
  머신 경로·샌드박스 제약은 당시 실행 방법이며 현재 환경의 영구 제약이 아니다.
  요구사항과 도메인 제약은 유지한다.
- 필요한 플러그인이 없으면 사용 가능한 도구로 같은 요구사항을 수행하고 대체
  방법을 보고한다. 필수 품질 검증을 수행할 수 없으면 누락을 명시한다.
  플러그인을 썼거나 독립 검증을 했다고 꾸미지 않는다.

## 개인정보와 도메인

- 실제 뱅크샐러드 파일·개인 거래 데이터·비밀값을 저장소나 생성 산출물에 넣지
  않는다. 테스트 데이터는 코드로 생성한 가짜 데이터만 사용한다.
- 비밀값은 문서에 `<...>` 자리표시로 쓴다. 저장소 밖에서 개인 데이터를 찾지 않는다.
- 가져오기 중복 판정·웹 수정 보호·거래 소유권·그룹 공개 범위·인증·쿠키·삭제
  동작을 바꿀 때 관련 설계와 호출 경로를 확인한다.
- UI 변경은 기존 디자인 토큰과 `src/common/` 부품을 우선한다.
  단순화를 이유로 보안·데이터 보존·접근성을 제거하지 않는다.

## 실행과 검증

명령의 상세 조건은 `docs/development.md`와 CI를 따른다.

- 웹: Node 버전은 `apps/web/.nvmrc`와 `package.json`의 engines를 따른다.
  동작 변경에 맞는 테스트를 수행하고, 웹 코드 변경의 최종 검증은
  `apps/web`에서 `npm run typecheck && npm test && npm run lint && npm run build`다.
- API: JDK 21과 Docker가 필요하다. `apps/api`에서 `./gradlew test`를 수행하고,
  업로드 한도·파서·메모리 관련 변경은 `./gradlew memoryTest`도 수행한다.
  API CI는 두 작업을 실행한다.
- 문서만 바꿨다면 링크·참조를, 설정만 바꿨다면 형식과 실제 설정값의 대응을
  검증한다. 앱 코드가 바뀌지 않았다는 이유를 적고 불필요한 전체 테스트는 생략할 수 있다.
- Docker·Gradle·네트워크·Git 쓰기 가능 여부는 실행 환경에서 확인한다.
  실행이 막혔으면 원인과 실행하지 못한 검증을 보고한다.
- 통과한 검증은 변경이나 새 실패 근거 없이 반복하지 않는다. 리뷰어는 구현자의
  결과를 코드와 대조하고, 구체적인 의문이 있을 때만 필요한 검증을 추가한다.

## 선택 도구

- Graphify 그래프가 있으면 관계 탐색에 활용하되, 현재 코드와 어긋난 그래프를
  최종 근거로 삼지 않는다. 그래프가 없으면 일반 검색으로 진행한다.
- Archify는 다이어그램이나 설명 페이지가 필요한 작업에서 사용한다.
- Ponytail의 작은 변경 원칙은 품질 조건을 생략할 이유가 되지 않는다.
- 플러그인·hook·watcher·Git hook·외부 LLM 호출을 이 문서만으로 설치하거나
  활성화하지 않는다. 해당 작업에 대한 사용자 요청이 있는 경우 수행한다.
- 선택 도구가 없다는 이유로 일반 구현·리뷰를 중단하지 않는다.

## 보고

한국어로 변경 내용·검증 결과·남은 제약을 간결하게 보고한다.
구체적 발견에는 파일과 위치를 붙이고, 추측과 확인한 사실을 구분한다.

## Pull Request

- PR 생성·수정 전 `.github/pull_request_template.md`와 관련 작업의 리뷰 조건을 확인한다.
- 제목은 기존 관례인 `type(scope): 한국어 변경 요약`을 따른다.
  scope가 필요 없으면 `docs: ...`, `chore: ...`처럼 생략한다.
- 본문은 `무엇 / 확인 / 리뷰 / 참고`로 작성한다. 변경 이유와 최종 동작을 먼저 쓰고,
  관련 스펙·계획·후속 과제가 있으면 연결한다. 없는 문서를 새로 만들 필요는 없다.
- 확인에는 실제 수행한 명령·결과와 생략한 검증 및 이유를 구분한다.
  경로 필터 때문에 CI가 실행되지 않은 것을 통과로 표현하지 않는다.
- 리뷰에는 수행 주체·범위·결과를 적는다. 자체 점검과 독립 리뷰를 구분하고,
  미실행 리뷰나 미해결 사항을 숨기지 않는다. 독립 리뷰가 필요한 작업은 공통 협업 규칙을 따른다.
- 생성 뒤 PR URL·base/head·draft 상태·병합 충돌·검증 상태를 확인하고 사용자에게 링크를 전달한다.
  병합 가능 상태는 테스트나 리뷰 통과를 의미하지 않는다. 사용자가 요청하지 않으면 병합하지 않는다.

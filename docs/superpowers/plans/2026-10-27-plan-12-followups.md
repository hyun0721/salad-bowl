# Plan 12 후속 과제

Plan 12(인증 보강)의 Task 리뷰, 반론 리뷰 2회(Codex gpt-6-astra/xhigh), 최종 리뷰(Claude opus)에서 나왔지만 넘긴 항목과 배포 주의다.

## 실행 중 바뀐 결정 (기록용)
설계 9장에 정리했다.
- refresh 쿠키 로그인 후 14일 고정(갱신 안 함)
- API는 프록시 요청만 받음(`PROXY_SECRET`)
- 로그인 제한 (이메일,IP) 5·IP 20·이메일 50, 저장소가 차면 fail-closed
- 더미 해시
- 세션 세대 + 재전송 전 사용자(sub) 확인

그 밖에:
- `sync-config`의 `deploy` 기본값을 `false`로 바꿨다. Pages를 먼저 배포하고 API를 배포하는 순서를 지키기 위함이다. Render 값을 바로 적용하려면 `deploy=true`나 Manual Deploy가 필요하다(`docs/deploy.md` 8·9장).
- 운영에서 `PROXY_SECRET`이 비었거나 32자 미만이면 API가 기동하지 않는다.
- 헬스체크 예외는 `GET /actuator/health` 정확한 경로 하나다.

## 배포 주의 (사용자가 직접)
`docs/deploy.md` "인증 보강(Plan 12)을 이미 운영 중인 서비스에 배포할 때"를 따른다.
- 머지 전에 해 둘 것:
  - GitHub Secret `PROXY_SECRET` 추가
  - Render·Pages(production·preview)에 같은 값을 직접 입력(지금 main의 sync-config에는 이 단계가 없다)
- 배포 뒤:
  - 기존 세션은 한 번 로그아웃된다(기존 refresh 쿠키에 `ver`가 없음).
  - 이후 로그인은 14일마다 다시 해야 한다.

## 받아들인 잔존 위험
- **이메일 전체 50회 잠금**: 여러 IP(예: 10개 × 5회)에서 남의 이메일로 틀리면, 정상 사용자도 15분 동안 429다. 완전히 막으려면 챌린지(CAPTCHA 등)나 다른 인증 경로가 필요하다.
- **제한 저장소 포화**: 미만료 키 50,000개(약 1,200개 IP에서 15분 동안 초당 약 27회 실패)를 채우면 새 (이메일,IP) 로그인이 비밀번호와 무관하게 429다. 포화 때의 `Retry-After: 60`은 실제 해제 시각을 보장하지 않는다. 신규 키 생성 예산을 IP 대역별로 두는 것이 다음 단계다.
- **메모리 제한·서버 1대 기준**: 재시작하면 제한이 초기화된다. 인스턴스가 늘면 Redis 등으로 옮긴다.
- **미리보기에 운영 비밀값**: push 권한자만 미리보기를 빌드하므로 지금은 둔다. 협업자가 늘면 미리보기 API·비밀값을 분리한다.
- **비밀값 교체 무중단 아님**: 키를 하나만 받아서, 교체할 때 Pages와 Render 배포 사이에 403 구간이 있다. 무중단으로 바꾸려면 구·신 두 키를 잠시 함께 받게 한다.
- **계정 존재 노출**: 회원가입의 `EMAIL_ALREADY_EXISTS`와 이메일 전체 제한의 `Retry-After`는 남는다.
- **액세스 토큰 15분**: 로그아웃해도 다른 기기의 액세스 토큰은 최대 15분 남는다.
- **프록시 비밀 불일치 403의 영향**: 클라이언트는 refresh 403을 세션 상실로 본다. 그래서 설정 오류나 배포 창에서는 사용자가 로그인 화면으로 간다.

## 나중에 (사소함)
- IP 검증은 문자 집합·길이만 본다(완전한 주소 정규화 아님).
- 제한 상태가 같은 Spring 컨텍스트의 테스트끼리 공유된다(테스트는 이메일·IP를 매번 새로 써서 피한다).

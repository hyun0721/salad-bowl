## 1. 개요와 목표

근로소득이 있는 회원이 카드사·홈택스에서 확인한 "신용카드 등 사용금액" 누계를 직접 입력하면,
해당 귀속연도 세법 기준으로 소득공제액을 계산하고, 남은 기간의 결제수단 배분을 비교해 보여 준다.

목표

- 회원이 자기 누계자료를 결제수단×소비구분 단위로 등록하고, 소비구분과 금액을 다시 볼 수 있다.
- 최저사용금액(총급여의 25%) 달성 여부, 소득공제액, 한도까지 남은 여유를 한 화면에서 확인한다.
- 같은 예산·같은 소비구분에서 결제수단만 바꿨을 때 공제액이 얼마나 달라지는지 비교한다.
- 관리자가 귀속연도별 세법 수치를 갱신하고, 과거 분석이 어떤 세법 버전으로 계산됐는지 추적한다.

대상

| 대상 | 설명 |
|---|---|
| 회원 | 근로소득이 있는 거주자 본인(일용근로자 제외). 그룹 가입 여부와 무관하다. |
| 서비스 관리자 | 연도별 세법 기준을 작성·적용하는 운영자. 그룹 관리자(그룹 ADMIN)와 다른 개념이다. |

## 2. 범위와 비범위

범위 (첫 출시)

- 개인 누계자료의 수동 등록·조회·수정·삭제
- 분석회차(누계 스냅샷) 생성·복사
- 소득공제액 계산과 소비구분·결제수단 비율 조회
- 남은 예산에 대한 결제수단 배분 비교와 추천
- 관리자의 연도별 세법 기준 관리

비범위

| 항목 | 상태 | 이유 |
|---|---|---|
| 그룹 단위 합산·공유 | 확정 (후속 고도화) | 사용자 확정사항 |
| 가계부 거래의 자동 합산 | 제안 | 거래에 신용/체크/현금영수증 구분과 전통시장·대중교통·문화체육 구분이 없다 (`V4__create_transactions.sql:22-27`). 매핑 설계가 따로 필요하다. |
| 실제 환급액(세액) 계산 | 제안 | 다른 공제·세율·기납부세액이 필요해 이 기능만으로 계산할 수 없다. |
| 부양가족 사용액 합산 | 제안 | 법 §126의2 ③으로 합산이 가능하지만 가족별 소득요건 확인이 필요하다. 첫 범위에서는 회원이 합산한 금액을 직접 입력하는 것까지만 허용한다. |
| 카드 혜택(포인트·할인) 최적화 | 제안 | 세법 계산과 무관하고 카드별 데이터가 없다. |
| 공제 제외 항목 자동 판별 | 제안 | 보험료·공과금·통신료 등 제외 항목(영 §121의2 ⑥)은 카드사·홈택스 자료가 이미 걸러 준 "공제대상액"을 입력받는다. |
| 임의 수식 실행 기능 | 제안 | 관리자는 숫자·조건만 설정한다. 산식 구조 변경은 코드 변경이다. |
| 회원 탈퇴 시 삭제 검증 | 제안 | 회원 삭제 기능 자체가 현재 없다. |

## 3. 용어

| 용어 | 뜻 |
|---|---|
| 귀속연도 | 사용금액이 속한 과세연도(1.1.~12.31.) |
| 분석회차 | 한 시점의 누계 스냅샷. 예: "10월 말 기준". 회차끼리 금액을 더하지 않는다. |
| 입력자료 | 회차에 붙는 출처별 누계자료 한 건. 예: 카드사 한 곳의 누계 조회 결과. |
| 결제수단 | 신용카드 / 체크·직불(기명식 선불 포함) / 현금영수증(소득공제용) |
| 소비구분 | 일반 / 전통시장 / 대중교통 / 문화체육. 가계부의 생활 카테고리와 다른 축이다. |
| 출처 | 카드사 / 홈택스 / 기타. 자료를 어디서 봤는지이며 결제수단이 아니다. |
| 공제대상액 | 출처가 공제 대상으로 집계한 사용금액. 입력 단위다. |
| 최저사용금액 | 총급여액의 25%. 전체 사용액이 이를 초과해야 공제가 시작된다. |
| 자녀등 | 2026 귀속부터 기본한도를 올려 주는 직계비속 요건 충족자(8.1절) |

## 4. 요구사항

상태 열: 확정 / 제안. "제안" 중 사용자 결정이 필요한 것은 결정 ID(D01~D15)를 붙였다.

### 4.1 접근·권한

| ID | 요구사항 | 상태 |
|---|---|---|
| TAX-01 | 회원은 본인의 소득공제 자료(회차·입력자료·금액·지출계획)를 개별로 등록한다. | 확정 |
| TAX-02 | 소득공제 자료는 소유 회원만 조회·수정·삭제한다. 다른 회원의 자료를 ID로 요청하면 존재 여부를 숨기고 404로 응답한다. | 제안 |
| TAX-03 | 소득공제 자료는 그룹 공개 설정·그룹 역할과 독립이다. 그룹 미가입·탈퇴·선택 그룹 변경이 접근을 막거나 자료를 공개하지 않는다. 서버 검사는 "요청자 = 소유자" 하나이며 그룹 접근 헬퍼(`GroupAccess`)를 쓰지 않는다. | 제안 |
| TAX-04 | 연도별 세법 기준은 서비스 관리자만 작성·수정·적용한다. | 확정 (수단은 D01) |
| TAX-05 | 서비스 관리자는 그룹 ADMIN과 별개의 권한이다. 그룹 역할을 세법 관리 권한으로 쓰지 않는다. | 제안 |
| TAX-06 | 일반 회원이 세법 관리 API를 호출하면 403, 세법 관리 화면에 URL로 들어오면 권한 없음 화면을 보여 준다. 서버가 요청마다 관리자 여부를 확인한다. | 제안 |
| TAX-07 | 로그아웃·세션 만료 시 소득공제 조회 캐시가 지워진다. 총급여·금액·작성 중인 값을 localStorage 등 브라우저 저장소에 두지 않는다. | 제안 |

근거: 현재 권한 규칙은 "인증 여부"뿐이고 역할이 없다(`SecurityConfig.java:70-75`, `User.java:18-43`).
그룹을 만든 회원은 자동으로 그 그룹의 ADMIN이 되므로(`GroupService.java:32`), 그룹 ADMIN을 재사용하면 모든 회원이 세법을 고칠 수 있다.
`GroupAccess.canViewOwnedBy/canEditOwnedBy`는 공개 중인 그룹 멤버·그룹 ADMIN에게 접근을 열어 주므로 급여 자료에 쓰면 안 된다.
로그아웃 시 `queryClient.clear()`가 전체 캐시를 비운다(`ClearCacheOnSignOut.tsx:10-13`). 쿼리 키 머리말은 `tax`처럼 기존 그룹 범위 키(`summary`, `bans` 등)와 겹치지 않게 한다.

D11 결정(2026-11-11): 업로드 메뉴를 없애 생긴 자리에 소득공제를 넣어 하단 탭 5칸을 유지한다.
현재 코드 대응: 월별 등록 현황은 `apps/web/src/imports/CoverageSection.tsx`, 업로드 이력은 `UploadPage.tsx:39-60`, 홈의 지난달 업로드 카드는 `HomePage.tsx:39-54`, 옛 경로 링크는 `HomePage.tsx:52`, 안내 문구는 `groups/NoGroupNotice.tsx:11`이다.
이 개편은 소득공제 자료와 무관한 기존 화면 변경이므로 개발 계획에서 소득공제보다 먼저 별도 PR로 나눌 수 있다.
관리자 메뉴 "연도별 세법 관리"는 하단 탭에 넣지 않는다. 진입 위치는 D01과 함께 정한다(사이드바·계정 시트 후보).

근거: 메뉴 원본은 정적 배열 `MENU` 하나이고 역할별 노출 기능이 없다(`menu.ts:3-17`).
하단 탭은 `MENU` 전체를 5칸 고정 격자로 그리고 하위 항목을 무시한다(`BottomTabBar.module.css:1`).
사이드바는 `children`으로 2단 구조를 바로 표현한다. 대시보드의 화면 안 메뉴가 좁은 화면 선례다.

## 6. 사용자 흐름과 화면 항목

회원 — 첫 등록

1. 소득공제 > 입력자료에서 "회차 만들기". 귀속연도·회차명·예상 총급여·근로기간(·자녀등 수)을 입력한다.
2. "자료 추가"로 출처별 누계자료를 넣는다. 자료명·출처·누계기간과 12칸 금액을 입력한다.
3. 통합 합계표에서 결제수단×소비구분 합계를 확인한다. 경고(출처 중복·기준일 불일치·미입력)가 있으면 여기서 본다.
4. 분석·지출계획으로 이동해 최저사용금액 달성, 공제액, 한도, 비율을 본다.
5. 남은 기간 지출계획을 입력하고 결제수단 배분 비교·추천을 본다.

회원 — 다음 달 갱신

1. 지난 회차를 복사해 새 회차를 만든다.
2. 각 자료의 기준일과 금액을 새 누계로 **덮어쓴다**(누계이므로 지난 회차에 더하지 않는다).
3. 분석을 다시 본다. 지난 회차는 그대로 남아 비교할 수 있다.

관리자 — 세법 갱신

1. 연도별 세법 관리에서 귀속연도를 고르고 초안을 만든다(직전 버전 복사 가능).
2. 수치·조건·근거·적용 대상 기간을 입력한다.
3. 검증을 통과하면 "적용". 적용 후에는 수정할 수 없다.
4. 그 귀속연도의 기존 회차에는 "새 세법 버전 있음"이 표시된다.

조회 항목과 분모

## 7. 계산·추천 정책

### 7.1 소득공제액 산식 (제안)

아래는 8.1절의 법령 조사 결과를 식으로 옮긴 것이다. 구현 전에 조문과 한 번 더 대조한다.

입력: 총급여 S, 통합 합계 12칸, 세법 버전의 수치.

1. 구분 합계를 만든다.
   - 전통 T = 전통시장 3칸 합, 대중 P = 대중교통 3칸 합
   - S ≤ 문화체육 기준이면: 문화 M = 문화체육 3칸 합, 직불등 B = 체크·직불 일반 + 현금영수증 일반, 신용 A = 신용 일반
   - S > 문화체육 기준이면: M = 0, B = 체크·직불과 현금영수증의 (일반 + 문화체육), A = 신용의 (일반 + 문화체육)
2. 최저사용금액 L = S × 25%. 전체(A+B+M+T+P)가 L 이하면 공제액은 0원이다.
3. 공제 가능 금액 = A×15% + (B+M)×30% + (T+P)×40% − 차감액
   - L ≤ A: 차감액 = L×15%
   - A < L ≤ A+B+M: 차감액 = A×15% + (L−A)×30%
   - 그보다 크면: 차감액 = A×15% + (B+M)×30% + (L−A−B−M)×40%
4. 기본한도 H를 귀속연도·급여구간·자녀등 수로 정한다.
5. 추가 인정액 = min(공제 가능 금액 − H, T×40% + P×40% + M×30%, 추가한도 상한). 공제 가능 금액이 H 이하면 0.
6. 소득공제액 = min(공제 가능 금액, H) + 추가 인정액

공제율·기준 비율·한도는 세법 버전의 값이다. 위 숫자는 2025·2026 귀속 값이다.

합성 예시 1 (2026 귀속, 총급여 4,000만원, 자녀등 없음)

| 구분 | 금액 |
|---|---|
| 신용 일반 A | 12,000,000 |
| 체크·현금영수증 일반 B | 3,000,000 |
| 문화체육 M | 500,000 |
| 전통시장 T / 대중교통 P | 1,000,000 / 500,000 |

L = 10,000,000 ≤ A이므로 차감액 = 1,500,000.
공제 가능 금액 = 1,800,000 + 1,050,000 + 600,000 − 1,500,000 = 1,950,000. 기본한도 300만원 이내이므로 소득공제액 1,950,000원.

합성 예시 2 (2026 귀속, 총급여 8,000만원, 자녀등 없음)

신용 일반 30,000,000 / 체크 일반 10,000,000 / 체크 문화체육 1,000,000 / 전통시장 2,000,000 / 대중교통 1,000,000.
총급여가 7천만원을 넘으므로 문화체육 100만원은 체크 일반으로 본다: A = 30,000,000, B = 11,000,000, M = 0.
L = 20,000,000 ≤ A, 차감액 = 3,000,000. 공제 가능 금액 = 4,500,000 + 3,300,000 + 1,200,000 − 3,000,000 = 6,000,000.
기본한도 2,500,000. 추가 인정액 = min(3,500,000, 1,200,000, 2,000,000) = 1,200,000. 소득공제액 3,700,000원.

### 7.2 추천 정책 (제안)

- 고정하는 것: 남은 예산 총액, 소비구분별 금액, 회원이 "결제수단 고정"으로 표시한 금액.
- 바꾸는 것: "바꿀 수 있는 금액"을 신용카드에 둘지, 체크·직불·현금영수증에 둘지.
  체크·직불과 현금영수증은 공제율이 같아 추천에서는 한 묶음으로 다룬다.
- 방법: (현재 누계 + 계획)을 7.1 계산기에 넣어 시나리오별 연말 예상 공제액을 구하고 비교한다. 별도 근사식(잔여한도 ÷ 공제율 등)을 쓰지 않는다.
- 보여 주는 시나리오: 현재 계획 / 공제액이 가장 큰 배분. 공제액이 같으면 현재 계획을 유지하고 "차이 없음"으로 표시한다.
- 이유 문구는 계산 결과에서 나온 사실만 쓴다. 예: "신용카드 사용액이 이미 최저사용금액을 넘어, 남은 일반 지출은 체크카드·현금영수증이 공제율 30%로 더 높습니다."
- 전통시장·대중교통은 결제수단과 무관하게 같은 공제율이므로 결제수단 추천 대상이 아니다. 문화체육은 총급여 7천만원 이하일 때 같다.
- 카드 포인트·할인·연회비·전월실적은 고려하지 않는다는 점을 가정에 적는다.
- "한도까지 필요한 소비액"은 "참고: 한도까지 남은 공제 여유"로 표현하고 소비를 늘리라는 문구를 쓰지 않는다.

## 9. 논리 데이터와 입력 검증

논리 개념이다. 물리 테이블 구성은 개발 설계에서 정한다.

| 개념 | 주요 항목 | 제약 |
|---|---|---|
| 세법 기준 | 귀속연도, 버전, 상태(초안/적용), 8.2절 설정값, 계산 알고리즘 버전, 근거, 적용 대상 기간, 작성자·적용자·시각 | 전역 데이터(회원 소유 아님). 적용본 불변. 귀속연도당 현재 적용 버전 하나 |
| 분석회차 | 소유 회원, 귀속연도, 회차명, 총급여, 근로기간, 자녀등 수, 세법 버전 | 소유 회원 삭제 시 함께 삭제. 세법 버전의 귀속연도와 일치 |
| 입력자료 | 회차, 자료명, 출처, 누계기간(시작일·기준일), 메모 | 회차에 종속 |
| 소비금액 | 입력자료, 결제수단, 소비구분, 공제대상액 | 원 단위 정수. 자료 안에서 (결제수단, 소비구분) 유일. 미입력과 0 구별 |
| 지출계획 | 회차, 소비구분별 예상액과 결제수단 고정액·변경 가능액 | 회차당 하나(D07) |

입력 검증

| 입력 | 규칙 | 상태 |
|---|---|---|
| 귀속연도 | 4자리 연도. 허용 범위는 D02 | 제안 |
| 회차명·자료명 | 필수, 앞뒤 공백 제거, 길이 상한(개발 설계에서 결정) | 제안 |
| 예상 총급여 | 필수, 1원 이상 정수. 비과세 소득을 뺀 연간 총급여라는 안내를 붙인다 | 제안 |
| 근로기간 | 귀속연도 안의 시작월~종료월, 시작 ≤ 종료 | 제안 (D03) |

## 10. 상태: 오류·미완료·삭제·재계산

| 상태 | 조건 | 화면 동작 |
|---|---|---|
| 회차 없음 | 회원에게 회차가 없다 | 빈 상태와 "회차 만들기" |
| 자료 없음 | 회차에 입력자료가 없다 | 입력자료: 빈 상태. 분석: "입력자료를 먼저 등록" |
| 미완료 | 미입력 칸이 하나라도 있다 | 입력자료에 미완료 표시. 분석은 결과를 확정값처럼 보여 주지 않고, 미입력 칸 수와 채우러 가는 링크를 보여 준다 |
| 합계 0원 | 모든 칸이 0 | 빈 차트. 공제액 0원 |
| 최저사용금액 미달 | 전체 ≤ 최저사용금액 | 공제액 0원, 달성까지 남은 금액 표시(소비 권유 문구 없이) |
| 추정 | 출처 중복 가능성 또는 기준일 불일치 | 결과에 "추정" 표시와 이유 |
| 세법 준비 중 | 귀속연도에 적용 버전이 없다 | 자료 저장은 가능, 분석은 계산하지 않음 |
| 새 세법 버전 있음 | 회차의 버전보다 새 적용 버전이 있다 | 알림과 "새 버전으로 다시 계산". 누르기 전에는 기존 버전 결과 유지 |
| 근로기간 확인 필요 | 근로기간이 1~12월 전체가 아니다 | 결과에 주의 표시(D03) |
| 입력 오류 | 검증 실패 | 해당 필드에 오류, 저장하지 않음 |
| 저장 충돌 | 다른 곳에서 먼저 수정됨 | D13에 따름 |
| 권한 없음 | 일반 회원이 세법 관리 접근 | 권한 없음 화면(403) |
| 없는 자료 | 없는 ID 또는 타인 자료 | 찾을 수 없음(404). 그룹 목록을 다시 불러오지 않는다 |
| 통신 오류 | 조회·저장 실패 | 오류 문구와 다시 시도. 입력한 값은 화면에 유지 |
| 삭제 | 회차·자료 삭제 | 확인 대화상자에 함께 지워지는 범위를 적는다. 복구 불가 |

- 근거: 2025 귀속 연말정산은 이미 끝났다. 2025는 자녀등 상향이 없고 2026부터 생겼으므로(법 ⑩ 단서, 부칙 제47조), 연도에 따라 입력란과 한도가 달라진다. 이 차이는 세법 버전의 "자녀등 단계별 한도"로 표현된다(8.2절).
- 질문: 첫 출시에 2026 귀속만 지원하면 될까요, 2025 귀속도 조회용으로 필요할까요?

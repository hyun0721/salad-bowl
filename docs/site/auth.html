인증과 권한 흐름

로그인 상태의 복원부터 거래 공개 범위까지, 브라우저와 API가 나누어 확인하는 규칙을 설명합니다.

코드 확인: 2026-10-30 · 기준 25d00f0

이 페이지에서인증과 권한은 따로 확인하기로그인과 토큰 보관새로고침·만료·동시 요청로그아웃과 세션 폐기Google 로그인과 계정 연동거래와 그룹의 권한 규칙수정할 때 확인할 시나리오

인증과 권한은 따로 확인하기

인증은 누가 요청했는지, 권한은 그 사람이 해당 데이터를 볼 수 있는지 판단하는 과정입니다. 웹의 로그인 화면이나 메뉴 숨김은 접근 제어의 최종 근거가 아닙니다.

  1. 운영 프록시가 요청 출처를 확인하고 서버용 X-Proxy-Secret을 붙입니다.
  2. API가 프록시 비밀값을 검사하고 JWT access 토큰으로 사용자 ID를 확인합니다.
  3. Service와 GroupAccess가 거래 소유권·그룹 멤버십·공개 범위·관리자 여부를 검사합니다.

/auth/**는 사용자 access 토큰 없이 호출할 수 있지만, 운영의 프록시 검사를 우회할 수 있다는 뜻은 아닙니다. 직접 Render로 보내는 요청은 health 예외 외에는 프록시 비밀값 검사를 받습니다.

로그인과 토큰 보관

항목보관·수명역할

Refresh JWTHttpOnly 쿠키 · 로그인 시점부터 기본 14일새 access 토큰 발급. JS가 직접 읽지 않음
운영 refresh 쿠키Path=/api/auth; SameSite=Lax; Secure브라우저가 인증 경로 요청에 전송

이메일 로그인은 POST /api/auth/login입니다. 서버는 비밀번호 해시를 확인하고 access 토큰을 JSON으로, refresh 토큰을 Set-Cookie로 반환합니다. 웹은 access 토큰을 보관하고 /api/me로 프로필을 조회합니다.

회원가입은 계정 생성 뒤 별도 로그인 요청을 보냅니다. 계정 생성은 성공했지만 자동 로그인은 실패할 수 있으므로, 이 상태를 가입 실패로 처리하지 않습니다. 비밀번호 로그인은 bcrypt 검증 전 시도 제한을 적용하고 존재하지 않는 이메일도 같은 방식으로 처리합니다.

새로고침·만료·동시 요청

페이지를 다시 열면 메모리 access 토큰은 사라집니다. AuthProvider가 refresh 쿠키로 POST /api/auth/refresh를 호출하고 성공하면 프로필을 읽어 로그인 상태를 복원합니다.

  • 인증된 API 요청이 401이면 API 클라이언트가 refresh를 시도하고 조건이 맞을 때 원래 요청을 한 번 재전송합니다.
  • 동시 refresh는 하나의 진행 중 요청을 공유합니다. 세션 세대와 토큰의 사용자 ID를 비교해 이전 로그인 요청이 새 계정 상태를 덮어쓰지 않게 합니다.
  • 토큰 없이 시작한 변경 요청은 다른 탭의 계정 쿠키로 잘못 재전송하지 않도록 자동 재시도를 제한합니다.
  • refresh의 401·403은 세션 해제로, 5xx·네트워크·잘못된 응답은 일시적 오류로 다룹니다. 서버 장애를 무조건 로그아웃으로 처리하지 않습니다.

서버의 refresh 응답은 새 refresh 쿠키를 심지 않습니다. 14일 수명을 계속 연장하거나 늦게 도착한 응답이 다른 세션 쿠키를 덮어쓰지 않도록 하기 위한 동작입니다.

로그아웃과 세션 폐기

POST /api/auth/logout은 유효한 현재 refresh 토큰의 버전을 기준으로 사용자의 tokenVersion을 올리고 쿠키를 지웁니다. 같은 계정의 기존 refresh 토큰은 이후 버전 검사에서 거절됩니다.

이미 발급된 access 토큰은 이 버전 검사 대상이 아니므로 즉시 모두 폐기된다고 해석하면 안 됩니다. 기존 access 토큰은 자체 만료까지 유효할 수 있습니다.

웹은 서버 로그아웃 성공 뒤 메모리 세션을 지웁니다. 서버 호출이 실패하면 로그인 상태를 유지하고 오류를 알립니다. signedIn에서 signedOut으로 바뀌면 React Query 캐시도 비워 다음 사용자에게 이전 조회 결과가 보이지 않게 합니다.

Google 로그인과 계정 연동

브라우저는 Google Identity Services에서 받은 ID 토큰을 POST /api/auth/google로 보냅니다. API가 서명·발급자·대상 클라이언트·만료를 확인한 뒤 기존 로그인과 같은 앱 토큰을 발급합니다. Google 토큰을 앱의 access 토큰으로 사용하지 않습니다.

  • 이미 연동된 google_sub가 있으면 해당 사용자로 로그인합니다.
  • 새 연동은 Google이 이메일을 확인한 경우에만 진행합니다. 같은 이메일의 기존 계정이 있으면 연결하고 기존 닉네임을 유지합니다.
  • 기존 계정이 없으면 새 계정을 만듭니다. Google 전용 계정에는 비밀번호가 없습니다.
  • 클라이언트 ID가 없으면 기능이 꺼집니다. 웹의 VITE_GOOGLE_CLIENT_ID와 API의 GOOGLE_CLIENT_ID가 일치해야 합니다.

승인된 JavaScript 원본과 설정 적용 순서는 배포 절차서의 Google 로그인 항목을 따릅니다. 클라이언트 보안 비밀이나 OAuth 리디렉션 URI를 사용하는 방식은 아닙니다.

sharedOwnerIds는 멤버십을 검사하지 않습니다. 호출 전에 requireMember가 필요합니다. canEditOwnedBy도 본인 거래에는 멤버십과 무관하게 true이므로 그룹 접근 검사 대신 사용하지 않습니다.

기능별 추가 조건은 해당 Service에서 확인합니다. 프런트에서 받은 userId·groupId를 권한의 근거로 신뢰하지 말고 인증된 사용자 ID와 서버의 관계를 기준으로 판단합니다.

수정할 때 확인할 시나리오

  • 로그인 → 새로고침 → access 만료 후 갱신 → 로그아웃.
  • 여러 요청이 동시에 401인 경우와 refresh의 일시적 서버 오류.
  • 요청 진행 중 로그아웃하거나 다른 계정으로 바꾼 경우.
  • 그룹 비멤버 접근, 일반 멤버의 관리자 기능 호출, 공개를 끈 소유자의 데이터 접근.
  • 잘못된 Origin·프록시 비밀값, 만료·잘못된 종류의 JWT.

관련 웹/API 테스트를 실행하고 로컬 쿠키 설정과 운영 쿠키 설정을 혼동하지 않습니다. 이 가이드는 동작 설명이며 새 보안 정책을 추가하는 문서는 아닙니다.

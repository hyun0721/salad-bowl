처음 시작하는 개발자 가이드

로컬에서 앱을 실행하고, 가짜 데이터로 기능을 확인한 뒤 필요한 검사를 수행합니다.

개발 도구와 작업 위치

Docker Desktop, JDK 21, Node 22.22 이상을 준비합니다. Node 주 버전의 원본은 apps/web/.nvmrc, 최소 버전은 package.json의 engines입니다. 아래 명령은 각 터미널을 저장소 루트에서 시작하는 기준입니다.

java -version
node --version
docker info

별도 워크트리를 쓰더라도 기본 포트와 Docker 리소스는 공유됩니다. 이미 개발 서버가 떠 있으면 중복 기동하지 말고 아래 검증 환경을 사용하거나 포트를 별도로 조정합니다.

DB → API → 웹 실행

터미널 1: 개발 DB

docker compose up -d

Postgres는 localhost:5432에서 실행되고 데이터는 pgdata 볼륨에 보관됩니다. 기존 데이터를 지우는 docker compose down -v는 초기 실행에 필요하지 않습니다.

터미널 2: API

cd apps/api
REFRESH_COOKIE_SECURE=false ./gradlew bootRun

기본 8080 포트에서 시작하며 Flyway가 스키마를 적용합니다. 로컬 HTTP는 Secure 쿠키를 사용할 수 없으므로 위 옵션을 둡니다. 운영에서는 Secure를 유지합니다.

터미널 3: 웹

cd apps/web
npm ci
npm run dev

localhost:5173에 접속합니다. 웹의 /api 요청은 Vite를 거쳐 API로 전달됩니다. 운영 주소나 비밀값을 가져올 필요는 없습니다.

첫 로그인과 기능 확인

  1. 로컬 로그인 화면에서 가짜 이메일·개발용 비밀번호로 회원가입합니다. 자동 로그인 뒤 홈이 열리는지 확인합니다.
  2. 새로고침해 세션 복원을 확인하고, 로그아웃 후 다시 로그인합니다.
  3. 그룹을 만들고 거래를 공개할 그룹을 선택합니다. 다른 회원의 화면을 확인하려면 별도 테스트 계정을 사용합니다.
  4. 거래 화면에서 가짜 거래를 추가합니다. 월별 등록 현황과 파일 업로드는 업로드 화면에서 확인합니다.

Google 로그인은 선택 기능입니다. 기본 이메일 로그인으로 개발을 시작할 수 있습니다. Google 기능을 수정할 때만 별도 클라이언트 ID를 웹과 API 양쪽에 설정하고 기존 배포 절차서의 로컬 설정을 따릅니다.

격리된 검증 데이터와 포트

반복 검증용 스크립트는 개발 DB 대신 별도 Postgres 컨테이너를 만듭니다. 먼저 웹 의존성 설치를 마치고 JDK·Docker·Python 3가 준비된 상태에서 저장소 루트에서 실행합니다.

bash .claude/skills/verify/bin/up.sh
bash .claude/skills/verify/bin/seed.sh
bash .claude/skills/verify/bin/doctor.sh

READY http://localhost:15173를 확인한 뒤 seed를 실행합니다. seed는 빈 검증 DB에서 한 번 실행하며 가짜 계정·그룹·엑셀 거래를 만듭니다. 계정 정보는 .claude/skills/verify/bin/env.sh를 참고합니다.

환경웹APIDB
일반 개발517380805432
격리 검증151731808055432

검증을 마치면 bash .claude/skills/verify/bin/down.sh로 검증 인스턴스를 내립니다. 검증 컨테이너의 데이터는 종료 시 사라집니다. 검증 환경도 고정 포트·컨테이너 이름을 사용하므로 워크트리 여러 곳에서 동시에 실행하지 않습니다.

화면별 이동과 확인 순서는 저장소의 기능별 검증 지도를 참고합니다. 실제 뱅크샐러드 파일·개인 거래는 테스트나 문서에 넣지 않습니다.

수정 내용에 맞춰 검사하기

웹 코드 변경: apps/web에서

npm run typecheck
npm test
npm run lint
npm run build

API 코드 변경: apps/api에서

./gradlew test

API 테스트에는 Docker가 필요합니다. 업로드 한도·파서·메모리를 바꿨다면 ./gradlew memoryTest도 수행합니다. API CI는 두 검사를 실행합니다.

문서만 변경했다면 게시 파일·링크·참조와 모바일/데스크톱 가독성을 확인합니다. HTML 작성만으로 앱 전체 검사를 다시 실행할 필요는 없습니다. 기능 검증은 성공한 단계와 실행하지 못한 단계를 구분해 기록합니다.

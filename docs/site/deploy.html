코드 배포와 성공 판정

  1. 변경 경로에 해당하는 PR 검사를 확인합니다. 웹은 web-ci, API는 api-ci, 공개 문서는 docs-pages / build입니다.
  2. main에 머지한 커밋을 기록하고 플랫폼의 배포 커밋과 비교합니다. Cloudflare는 CI 완료를 기다리는 구성이 아니므로 머지 전에 검사를 확인합니다.
  3. Render는 배포가 Live인지 확인하고 실제 기능의 API도 호출합니다. health의 UP만으로 새 기능 반영을 판정하지 않습니다.
  4. 웹에서는 첫 조회, 새로고침, 오류 후 재시도, 로그인 유지를 확인합니다. PWA가 이전 앱 셸을 사용 중이면 업데이트 알림의 새로고침도 확인합니다.

웹과 API의 배포는 동시에 끝나지 않습니다. 새 엔드포인트가 필요한 화면은 서버 선배포 후 공개합니다. Cloudflare 미리보기 역시 운영 API·DB를 사용하므로 데이터 변경은 별도 확인용 계정으로 수행합니다.

변경 경로 때문에 검사가 생략된 것은 통과와 다릅니다. 경로 필터가 있는 web-ci·api-ci를 무조건 필요한 검사로 지정하지 않는다는 저장소의 운영 지침도 확인하세요.

환경변수 변경과 적용

원본 위치: 저장소 Settings → Environments → production. DB_*, JWT_SECRET, PROXY_SECRET, 플랫폼 API 키는 Secrets, 서비스 ID·주소·Google 클라이언트 ID 등은 Variables에 둡니다. 전체 이름과 초기 값 형식은 기존 배포 절차서의 설정 표를 따릅니다.

  1. GitHub의 원본 값을 수정합니다. production 배포 브랜치는 main으로 제한합니다.
  2. Actions → sync-config → Run workflow에서 main과 dry_run=true를 선택해 값 형식을 검사합니다. 이 실행은 플랫폼 API 연결을 검증하지 않습니다.
  3. dry_run=false로 반영합니다. deploy=true는 Render 재배포까지 요청하며 기본값은 false입니다.
  4. Cloudflare의 최신 production 배포를 Retry합니다. 동기화만으로 기존 배포가 갱신되지는 않습니다. 웹의 VITE_* 값은 빌드할 때 들어갑니다.
  5. Render 재배포 완료와 Cloudflare 배포 완료 후 실제 동작을 확인합니다.

PROXY_SECRET 교체는 양쪽 값을 맞춘 뒤 Cloudflare를 먼저 재배포하고 API를 배포합니다. 전환 중 이전·새 비밀값이 섞이면 요청이 403으로 실패할 수 있습니다. JWT_SECRET 교체는 기존 세션에 영향을 주므로 모든 사용자의 재로그인을 예상합니다.

예외적으로 keepalive의 API_HEALTH_URL은 저장소 Actions Variable에 둡니다. Google 로그인을 끌 때는 빈 값 동기화가 삭제를 수행하지 않으므로 Render·Cloudflare 값도 제거하고 재배포해야 합니다.

배포 후 확인할 것

저장소 루트에서 실제 앱 주소로 실행합니다. 아래 주소는 자리표시입니다.

scripts/smoke.sh 'https://<project>.pages.dev'

failures: 0과 개별 PASS를 확인합니다. 이 스크립트는 정적 파일·보안/캐시 헤더·health·인증 없는 API 응답을 검사하며 계정을 생성하지 않습니다. 로그인·업로드·그룹 권한까지 검사하는 도구는 아닙니다.

  • 웹: Cloudflare 배포 커밋과 실제 화면 확인.
  • API: Render Events·Logs에서 기동·DB 연결·오류 확인.
  • 인증: 테스트 계정 로그인 → 새로고침 → 로그아웃 확인.
  • 문서: Actions → docs-pages → 성공한 실행의 배포 URL 확인. 파일 묶음은 실행 하단 Artifacts → github-pages에서 확인.

콜드스타트·파일 한도·메모리 관측치는 한계점에 있습니다. 무료 플랜 조건과 대시보드 메뉴는 바뀔 수 있으므로 서비스에서 현재 값을 확인하세요.

되돌리기와 DB 경계

웹은 Cloudflare의 이전 배포로 Rollback, API는 Render에서 이전 커밋을 지정해 Manual Deploy합니다. 문서는 이전 문서 변경을 되돌린 커밋을 main에 반영해 다시 배포합니다.

Flyway는 앱 롤백과 함께 되돌아가지 않습니다. 이전 앱이 현재 스키마를 읽을 수 있는지 먼저 확인합니다. refresh 토큰 폐기 검사가 없던 옛 인증 코드로 돌아가면 폐기된 토큰을 다시 받을 수 있으므로 기존 배포 절차서의 JWT 비밀값 교체 절차도 필요합니다.

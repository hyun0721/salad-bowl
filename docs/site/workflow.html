세션과 worktree의 수명 주기

작업 하나는 브랜치 하나와 worktree 하나를 쓰고, 병합과 함께 끝납니다. 시작부터 정리까지 순서대로 무엇을 만들고 언제 지우는지 설명합니다.

코드 확인: 2026-11-02 · 기준 398b05c와 이 문서를 도입한 PR

이 페이지에서한눈에 보기무엇이 어디에 사는가단계별 순서세션을 넘겨 이어 가기정리 대상 판단자주 막히는 상황정하지 않은 것

작업의 수명은 worktree가 정하고, 세션은 그 안에서 짧게 이어집니다

세 가지만 기억하면 됩니다.

  • 작업 하나에 브랜치 하나, worktree 하나를 씁니다. 브랜치는 한 번에 한 worktree에서만 열 수 있습니다.
  • 한 worktree에서 세션이 여러 번 이어질 수 있습니다. 세션이 끝나도 작업이 끝난 것은 아닙니다.
  • 다음 세션과 main에 남는 것은 커밋한 파일과 PR뿐입니다. 임시 산출물은 worktree를 지울 때 함께 사라집니다.

무엇이 어디에 사는가

수명이 다른 것을 한곳에 두면 정리할 때 헷갈립니다. 아래 표에서 각 항목이 어디에 있고 언제까지 남는지 확인합니다.

항목위치남는 기간공유 범위
기본 체크아웃저장소 루트계속main만 둡니다. 새 작업을 여기서 시작하지 않습니다.
Claude worktree.claude/worktrees/<이름>작업 시작부터 병합까지해당 작업 하나
Codex worktree~/.codex/worktrees/<id>/salad-bowl작업 시작부터 병합까지해당 작업 하나. Codex 앱이 만듭니다.
.git저장소 루트계속모든 worktree가 브랜치, 원격 정보, stash를 공유합니다.
세션Claude나 Codex의 대화분에서 시간 단위대화 내용은 다른 세션에 전달되지 않습니다.
brief와 보고.superpowers/sdd/<작업명>/worktree와 같음git이 무시합니다. 같은 worktree의 세션만 읽습니다.
캡처와 로그tmp/ (Playwright는 tmp/playwright/)worktree와 같음git이 무시합니다.
Graphify 그래프graphify-out/worktree와 같음worktree 사이에 자동으로 공유되지 않습니다. 새 worktree에서 다시 만듭니다.
의존성과 빌드 결과worktree 안의 node_modules/ 등worktree와 같음2026-11-02에 측정한 worktree 대부분이 340~450MB였습니다.
검증 스택, 개발 DBDocker와 로컬 포트 (DB 55432, API 18080, 웹 15173)down.sh 실행 때까지컴퓨터 전체가 공유합니다. 한 번에 하나만 띄웁니다.

단계별 순서

1. 시작하기 전에 기본 체크아웃을 확인합니다

기본 체크아웃이 main이고 깨끗해야 합니다. 이전 작업의 worktree가 남아 있으면 먼저 정리 대상을 판단합니다.

git fetch --prune origin
git status -sb
git worktree list

2. 최신 main에서 worktree를 만듭니다

새 작업은 항상 origin/main에서 시작합니다. 병합한 브랜치를 다시 쓰지 않고 새 이름을 붙입니다. 이름을 재사용하면 이전 PR의 커밋과 새 커밋이 섞여 범위가 흐려집니다.

git worktree add .claude/worktrees/<작업명> -b <type>/<작업명> origin/main

Claude Code와 Codex 앱은 각자 worktree를 만들 수 있습니다. 어느 쪽이 만들었든 같은 규칙으로 정리합니다.

그다음 작업 크기를 정합니다.

  • 한 세션에서 끝나면 대화에서 설계 승인을 한 번 받고 바로 구현합니다. 스펙과 계획 문서는 쓰지 않고, 설계 결정은 PR 본문의 "무엇"에 남깁니다.
  • 여러 세션이나 여러 PR에 걸치거나, 다른 세션이 이어서 실행하거나, 가져오기 중복 판정·웹 수정 보호·거래 소유권·그룹 공개 범위·인증·쿠키·삭제 동작을 바꾸면 docs/superpowers/specs/와 plans/에 문서를 커밋합니다.

기존 스펙이 있으면 최신 main 기준으로 현재 코드와 맞는지 먼저 대조합니다.

3. 구현합니다

  • 같은 변경을 구현하는 담당자는 한 번에 한 명입니다. 다른 실행기의 미완료 변경을 덮어쓰지 않습니다.
  • Claude 세션은 codex-collab의 역할 표를 따릅니다. 구현하지 않은 쪽이 리뷰를 한 번 맡습니다.
  • 계획 문서가 없는 작업의 brief와 보고는 .superpowers/sdd/<작업명>/에 짧게 둡니다. brief에는 요구사항과 정확한 값만 쓰고 구현 코드를 미리 쓰지 않습니다.
  • 화면 캡처는 tmp/에 둡니다. Playwright MCP는 .mcp.json의 --output-dir tmp/playwright로 이미 그 위치에 저장합니다.
  • 검증 스택은 컴퓨터에 하나입니다. 포트가 이미 사용 중이면 다른 세션의 스택이므로 건드리지 않고, 검증을 실행하지 못했다고 보고합니다. down.sh는 이번 세션이 띄운 스택에만 실행합니다.

4. 검증하고 리뷰합니다

웹 코드를 바꿨다면 apps/web에서 npm run typecheck && npm test && npm run lint && npm run build를 실행합니다. API 코드를 바꿨다면 apps/api에서 ./gradlew test를 실행하고, 업로드 한도·파서·메모리를 바꿨다면 ./gradlew memoryTest도 실행합니다. 문서만 바꿨다면 링크와 참조를 확인합니다. 독립 리뷰는 구현하지 않은 쪽이 한 번만 합니다.

5. PR을 엽니다

PR 제목은 type(scope): 한국어 변경 요약 형식을 따르고, 본문은 무엇 / 확인 / 리뷰 / 참고로 씁니다. 화면이 바뀌면 375px 이전·이후 캡처를 "확인"에 표로 넣습니다. 이미지는 pr-assets 브랜치의 pr-<번호>/에 올리고 main에는 커밋하지 않습니다. 병합은 사용자가 요청할 때만 합니다.

6. 병합하면 바로 정리합니다

병합한 순간 브랜치와 worktree는 역할을 마쳤습니다. 기록은 main에 남아 있고, PR 페이지의 Restore branch 버튼으로 브랜치도 되살릴 수 있습니다.

git switch main && git pull --ff-only
git worktree remove <worktree 경로>
git branch -d <브랜치>

쌓인 것이 여러 개면 스크립트가 병합된 브랜치만 골라 지웁니다. 기본은 dry-run이고, 실제 삭제는 RUN=1을 붙여야 합니다.

scripts/git-cleanup.sh          # 지울 목록만 출력
RUN=1 scripts/git-cleanup.sh    # 실제로 삭제

병합 뒤에 수정이 더 필요하면 2단계로 돌아가 origin/main에서 새 브랜치를 만듭니다.

7. 세션을 닫기 전에 상태를 확인합니다

작업이 끝나지 않았어도 세션은 닫힙니다. 닫기 전에 아래 셋을 확인합니다.

git status -sb                  # 커밋하지 않은 변경
git log origin/<브랜치>..HEAD    # 푸시하지 않은 커밋
gh pr list --head <브랜치>       # 열린 PR

세션을 넘겨 이어 가기

무엇이 다음 세션에 전달되는지는 이어 가는 장소로 정해집니다.

상황전달되는 것할 일
같은 worktree에서 Claude와 Codex가 교대커밋하지 않은 변경, .superpowers/sdd/의 brief와 보고담당자를 한 명으로 정합니다. 다른 쪽의 미완료 변경을 덮어쓰지 않습니다.
다른 worktree나 다른 날 세션에서 이어 감푸시한 브랜치와 커밋한 계획 문서만계획 문서를 커밋하고 브랜치를 푸시합니다. .superpowers/는 넘어가지 않습니다.
작업을 잠시 중단푸시한 커밋미완료 변경을 WIP 커밋으로 푸시합니다. stash는 모든 worktree가 공유하므로 오래 두지 않습니다.
같은 브랜치를 다른 worktree에서 열고 싶음열리지 않음먼저 열려 있는 worktree를 정리하거나 그 worktree에서 이어 갑니다.

다른 세션이 이어서 실행해야 하는 작업은 계획 문서가 필요하다는 것이 공통 작업 규칙입니다. .superpowers/를 git이 무시하는 이유도 같습니다. 인수인계 수단이 아니라 한 worktree 안의 작업 메모이기 때문입니다.

정리 대상 판단

git worktree remove는 --force 없이 실행하면 커밋하지 않은 수정이나 추적하지 않는 새 파일이 있는 worktree를 거부합니다. git이 무시하는 파일(tmp/, .superpowers/, graphify-out/)만 남았다면 거부하지 않습니다. 그래서 스크립트는 --force를 쓰지 않고, 거부된 브랜치는 건너뛰고 이유를 출력합니다.

상태처리
병합했고 변경 없음, 또는 무시되는 파일만 남음scripts/git-cleanup.sh가 지웁니다.
병합했고 무시되지 않는 새 파일(예전 브랜치의 스크린샷 등)이 남음필요한 파일이 없는지 목록을 본 뒤 git worktree remove --force로 지웁니다.
병합했고 추적하는 파일이 수정됨수정 내용을 확인합니다. 이미 main에 있으면 버리고, 아니면 새 브랜치로 옮긴 뒤 지웁니다.
병합하지 않음 (PR이 열려 있거나 main에 없는 커밋이 있음)지우지 않습니다. 스크립트는 이런 브랜치를 건너뜁니다.
원격 브랜치가 삭제되어 [gone]으로 표시됨병합 때문인지 PR로 확인합니다. 병합한 PR이면 위 행을 따릅니다.

스크립트는 브랜치가 origin/main의 조상인지로 병합 여부를 판단합니다. merge commit으로 병합할 때만 맞습니다. squash merge로 바꾸면 병합한 브랜치도 미병합으로 보여 아무것도 지우지 않으므로, 그때는 gh pr list --state merged의 브랜치 이름을 기준으로 바꿉니다.

자주 막히는 상황

증상원인조치
contains modified or untracked files, use --force to delete itworktree에 수정이나 추적하지 않는 파일이 있습니다.git -C <경로> status로 목록을 확인합니다. 필요 없으면 --force를 붙입니다.
Cannot delete branch '…' checked out at '…'다른 worktree가 그 브랜치를 열고 있습니다.해당 worktree를 먼저 제거한 뒤 브랜치를 지웁니다.

사라진 줄 알았던 변경이 git stash list에 있음stash는 모든 worktree가 공유합니다.내용을 확인하고 필요하면 브랜치에 적용한 뒤 git stash drop으로 지웁니다.

정하지 않은 것

  • 세션 종료 훅으로 자동 정리하지 않습니다. 세션이 끝나도 작업이 끝난 것은 아닙니다. 미완료 브랜치의 brief를 훅이 지우면 이어 갈 수 없습니다. 병합 뒤 정리 단계와 무시 규칙으로 충분하고, 필요해지면 병합한 브랜치의 worktree에만 적용합니다.
  • squash merge로 바꾸지 않았습니다. 바꾸게 되면 정리 스크립트의 병합 판정부터 고칩니다.
